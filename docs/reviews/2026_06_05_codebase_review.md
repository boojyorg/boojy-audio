# Boojy Audio — State-of-the-App Review

**Date:** 2026-06-05
**Version under review:** v0.5.1 (`pubspec 0.5.1+6`, draft release cut 2026-06-05, not yet tagged/published), dogfood phase. v0.6 "Sound" / drum-kit work already in flight on side branches.
**Scope:** whole-app correctness audit — Rust engine (realtime, DSP, persistence), VST3 hosting, the FFI/lock boundary, Flutter screens + command/undo layer, round-trip fidelity, testing, and repo/CI. Improve the app, *not* add features.
**Extends:** `docs/reviews/2026_05_29_codebase_review.md` (the v0.3.0 audit that drove the v0.3.x/v0.5 trust theme). This is the next major-boundary read; it does not repeat that report's resolved items.

**How this review was produced:** a deep parallel read of every subsystem, a multi-lens bug hunt, then **adversarial verification** — every candidate defect was re-checked by independent skeptics trying to refute it. **41 defects survived; 23 were refuted and dropped.** Each survivor carries a `file:line` and a cheap repro. All findings are **code-confirmed** — confidence is at the source level; no headless GUI click-through was run, so runtime-repro steps are the predicted behaviour from the code, noted for manual confirmation.

> **Read this first:** the suite is green and the v0.3-era criticals (per-sample VST3, mono export, stale-id-on-redo for effects/returns) were largely addressed across v0.3.x–v0.5. This review is about the **next layer of latent correctness bugs** — almost all of them are *silent*: wrong loudness, wrong delay time on a 44.1 kHz device, a clip that plays from the wrong beat after undo, a project that drops a clip on reload, a UI that freezes with no log. The happy path the dev tests on is solid. The app is still fragile under **non-default audio hardware, real plugin loads, untrusted project files, and the undo/redo paths a dogfooder hits every session.**

---

## 1. Executive summary + scorecard

Boojy Audio has matured into a competent alpha DAW. The v0.3→v0.5 hardening cycles paid off: the realtime path now uses lock-free atomics + try-lock-or-count for the heavy locks, has a NaN/Inf guard at the DAC boundary, sub-block VST3 chunking, and FTZ/DAZ denormal flush; the FFI boundary keeps its panic-guard discipline; the persistence layer round-trips CC, time signature, and backward-compat defaults correctly. **No critical realtime violation remains on the default device.** But this deeper read surfaced two structural problems and a long tail of silent correctness bugs.

The two structural problems:

- **The whole engine assumes a 48 kHz device.** Delay, Chorus, Reverb, the synth filter, the recorder, and VST3Effect all hardcode `TARGET_SAMPLE_RATE` and none implement a working `set_sample_rate`. On the 44.1 kHz interfaces that are common on macOS and Windows, **every time-based effect is ~8.8% wrong** (a 500 ms delay becomes 544 ms), recorded audio plays back 8.84% too fast/sharp, and switching devices mid-session pitch-shifts every VST3 plugin. This is one root cause expressed as eight separate confirmed bugs (C2, C4, C6, C9, C11, C22, C26, plus the count-in math C71).
- **The undo graph has holes on the paths dogfooders use most.** MIDI clip move never updates the engine start time (C46/C63 — *critical*), MIDI clip delete-undo-redo leaves a stale ID ghost-playing (C45), track reorder / clip consolidation / sampler-drag are entirely outside the undo graph (C49/C50/C54), and duplicate-track undo leaks orphaned clips and plugin windows (C47). A musician who drags a clip and presses Cmd+Z hears the clip from the *old* position while the UI shows the new one.

The most insidious theme is again **silent correctness**: there is no critical that crashes today, but a project can be **quietly corrupted on reload** (audio clips dropped when a track has >1 clip — C66; held notes dropped on save — C65), an export can be **silently wrong** ("Export for Spotify" applies no LUFS at all — C16; stem exports apply fader before FX while the full mix applies it after — C68), and a save can **report success while having failed** (C55), redirecting auto-save at a corrupt path. None throw an error. None are exercised by the green suite.

The one **critical lock bug** (C32) is a genuine AB/BA deadlock between the stopped-path audio callback and the add/remove-effect API — and the stopped path is the *dominant* dogfooding state. It freezes the UI with no log.

The bright spots are real: the playing-path lock hygiene, the snapshot patterns in `sends.rs`, the biquad/sampler envelope math, the dual-source persistence split, and the green core-pipeline regression tests are all solid. But the engine `api/` + `ffi/` layers still have **zero unit tests**, and the local post-edit hook gates a **measurably weaker bar than CI** for both Rust and Dart lint, so a dev can iterate to "clean" locally and still red CI.

**One-line take:** nothing crashes on the dev's Apple-Silicon / built-in-output happy path, which is exactly why a cluster of *silent* sample-rate, undo, and round-trip bugs has accumulated unseen. The next theme should be **"correct on real hardware, honest about failure"**, not features.

## 2. Confirmed bugs (severity-ranked)

41 adversarially-confirmed defects. All are **code-confirmed**; interactive GUI repro was not run, so repro steps are the predicted behaviour from source. The green suite covers none of these paths. IDs are non-contiguous (refuted candidates were dropped, see §4).

### Critical

- **C32** — **Lock-order inversion deadlocks the UI on add/remove-effect while stopped** — `engine/src/audio_graph/renderer.rs:566-572`. The `!is_playing` branch takes `effect_manager.lock()` (566) then `track_manager.lock()` (572) for the whole buffer; `add_effect_to_track`/`remove_effect_from_track` (`engine/src/api/effects.rs:18-19`) take them in the opposite order. Classic AB/BA deadlock — UI freezes silently, no log. Fires on the dominant dogfooding workflow (editing FX while stopped). *Repro: stop playback, call `add_effect_to_track_ffi` from Dart with the output stream active — hangs within a callback period.*
- **C46 / C63** — **MIDI clip move undo/redo never updates the engine start time** — `ui/lib/services/commands/clip_commands.dart:1108`. `execute()`/`undo()` only call `onClipMoved` → `updateClip()` → `_scheduleMidiClipPlayback()`, which re-adds notes but never calls `setClipStartTime` (that only happens in `rescheduleClip()`, line 443). The engine plays the clip from the old position while the UI shows the new one — on *every* drag-move and every undo, not just an edge case. *Repro: clip at beat 1, drag to beat 5, Cmd+Z — snaps back visually, engine still plays from beat 5.*

### High

- **C1** — **Two blocking `.lock()` calls on the playing audio hot path** (tempo + recording state) — `engine/src/audio_graph/renderer.rs:737` (and `:821`). Plain `.lock()` instead of the try-lock-or-count the same subsystem uses elsewhere. A UI thread holding either lock (tempo drag, record start) stalls the audio thread → underrun. *Repro: hold a tempo-drag while playing.*
- **C2 / C9** — **Delay/Chorus/Reverb hardcode 48 kHz; broken on 44.1 kHz devices** — `engine/src/effects.rs:692` (Delay `get_delay_samples`), `:1083` (Chorus LFO), `:772/:778` (Reverb comb/allpass). None override `set_sample_rate`; the dispatch at `effects.rs:1204-1207` reaches the no-op default. A 500 ms delay measures ~544 ms; reverb tail is pitched. *Repro: 44.1 kHz interface, Delay set to 500 ms.*
- **C7** — **Synth release envelope anchors to `params.sustain`, not the level at note-off** — `engine/src/synth.rs:219`. Release computes `sustain * (1 - progress)`; note-off during attack/early-decay jumps discontinuously to 0.7 → audible click. The sampler does this right (`sampler.rs:83/228`). The synth is the default instrument, so every staccato note hits it. *Repro: tap a key < ~110 ms with default ADSR.*
- **C10** — **Voice stealing always cuts voice[0] with no release ramp** — `engine/src/synth.rs:380` (and `sampler.rs:570`). Stolen voice gets immediate `note_on()` (phase reset, env→0), discarding its sample with no crossfade → hard click on the 9th+ simultaneous note. *Repro: sustain pedal + 10-note chord (>MAX_VOICES=8).*
- **C16** — **PlatformTarget LUFS normalization is dead code — "Export for Spotify" is a no-op** — `engine/src/export/wav.rs:69`. `platform_target` is defined, exposed via `with_platform()`, documented to apply −14 LUFS etc., but neither `export_wav()` nor `export_mp3()` ever reads it or calls `normalize_lufs()`. Silently wrong loudness. *Repro: export with Spotify target, measure LUFS.*
- **C17** — **`set_quantize` ignores `note_division` — all non-zero values give a hardcoded 1/16 grid** — `engine/src/midi_recorder.rs:200`. `update_quantize_grid()` always computes `samples_per_beat / 4`; the argument is only logged. `set_quantize(4)` (quarter) and `set_quantize(32)` (32nd) both produce 1/16. *Repro: `set_quantize(4)` then record.*
- **C26** — **VST3Effect has no `set_sample_rate` — device switch pitch-shifts every plugin** — `engine/src/vst3_host.rs:842`. Inherits the no-op default; the dispatch at `effects.rs:1209` does nothing. Switch built-in 44.1 kHz → 48 kHz interface mid-session and every VST3 runs at the stale rate (≈9% sharp, aliasing). Fix: deactivate/reinit/activate on rate change. *Repro: load a VST3 synth at 44.1 kHz, switch to 48 kHz, play a note.*
- **C33** — **Null-pointer UB at the FFI boundary** — `engine/src/ffi/tracks.rs:25`. `create_track_ffi` passes `track_type`/`name` straight to `CStr::from_ptr` with no `is_null()` guard; UB happens inside the unsafe block before `ffi_catch` can catch a panic. Same in `add_effect_to_track_ffi` (`effects.rs:19`) and `sends.rs:13/44/81`. Dart guarantees non-null today, but any Dart-side bug → instant process termination. *Repro: `create_track_ffi(null, ...)` from a C harness.*
- **C34** — **Track-name comma injection corrupts CSV field offsets** — `engine/src/api/tracks.rs:307`. `get_track_info` emits `id,name,type,volume_db,…` with `name` unescaped at index 1. Rename a track to "Drums, Kit" and `TrackData.fromCSV` (`ui/lib/models/track_data.dart:35-51`) shifts every later field — `parts[2]` (type) and `parts[3]` (volume_db) mis-parse. Silent data corruption, not a crash. *Repro: rename a track to "Vocals, Lead", call `getTrackInfo`.*
- **C37** — **`_consolidateSelectedClips` bypasses undo — Cmd+J is permanent** — `ui/lib/screens/daw_screen.dart:2406`. The wired private method (Cmd+J / Edit menu, lines 4046/4088) calls `deleteClip()`+`addClip()` directly; the correct `DAWClipMixin.consolidateSelectedClips` (`daw_clip_mixin.dart:340`) wraps a `CompositeCommand` but is dead. *Repro: select 3+ clips, Cmd+J, Cmd+Z — clips don't return.*
- **C38** — **PianoRoll `dispose()` doesn't call `stopAudition()` — MIDI note stuck on** — `ui/lib/widgets/piano_roll.dart:164`. Click a note (NoteOn sets `currentlyHeldNote`) then close the editor; NoteOff is never sent and the voice sustains indefinitely for sustained patches. *Repro: click a note, immediately close the editor panel.*
- **C45** — **`DeleteMidiClipFromArrangementCommand`: double engine remove → stale ID on redo** — `ui/lib/services/commands/clip_commands.dart:1078`. `execute()` calls `removeMidiClip` then `onClipRemoved` calls it again (no-op). On undo, `addRecordedClip` gets a *new* Rust ID; on redo, `execute()` removes the original (now-stale) ID → no-op, clip keeps playing. *Repro: record clip → Cmd+Del → undo → redo — still audible.*
- **C47** — **`DuplicateTrackCommand.undo()` has no UI teardown — leaks clips + state** — `ui/lib/services/commands/track_commands.dart:368`. Calls `engine.deleteTrack` but no `onCleanup`; unlike `DeleteTrackCommand`, it leaves orphaned MIDI clips in `midiPlaybackManager`, a dangling `trackController` entry, and possibly open plugin windows. Orphans can ghost-play on next transport start. *Repro: duplicate a MIDI track with clips → Cmd+Z — track gone from mixer, clips remain on timeline.*
- **C55** — **`saveProjectToPath` returns `success:true` even when the engine returns `Error:`** — `ui/lib/services/project_manager_native.dart:127-138`. Never checks the `Error:` prefix before setting `_currentProjectPath = path` (134). Auto-save then targets the corrupt path; the UI shows green "saved". The *load* path guards this (74); the save path doesn't. *Repro: fill disk near-capacity, save — status shows success, reopen reveals partial project.json.*
- **C65** — **Stuck/active MIDI notes silently dropped on save** — `engine/src/audio_graph/project.rs:843`. `convert_midi_events_to_notes()` accumulates `active_notes` but never flushes notes still "on" at end-of-loop. Any held note is discarded on reload. *Repro: record a clip, save mid-playback while a long note sustains, reload.*
- **C66** — **Audio clips silently dropped on reload (>1 clip per track)** — `engine/src/api/project.rs:138`. The restore loop only `eprintln!`s when `audio_file_id` isn't in `clips_map` and continues; no error to the caller. The AudioFileData-ID-as-clip-ID conflation means a track with multiple audio clips drops clips on reload, and a moved/renamed asset loses data with no dialog. *Repro: save, move one .wav out of the .audio folder, reload — track empty, no error.*
- **C68** — **Stem export applies fader/pan before the FX chain; full-mix applies it after** — `engine/src/audio_graph/offline.rs:796`. `render_track_offline()` gains in Pass 1 (pre-FX); `render_offline()` gains in Pass 3 (post-FX). Stems feed a pre-fader signal into compressors/EQ → different loudness and timbre than the mix. *Repro: compressor on a track, export stems vs full mix, compare.*
- **C69** — **Zero unit tests in `engine/src/api/` and `engine/src/ffi/`** — `engine/src/api/project.rs:1`. The entire API layer (save/load, recording, send routing, VST3 mgmt, export) and all FFI shims have no `#[cfg(test)]`. Every regression must be caught by full e2e or manual testing — and the bugs above live exactly here.
- **C76** — **Post-edit hook runs `cargo clippy` without `-D warnings` — passes what CI rejects** — `.claude/hooks/post-edit-validation.sh:59`. CI runs `clippy --all-targets -- -D warnings`; the hook exits 0 on warnings. Dev iterates green locally, reds in CI. CLAUDE.md:61 documents the correct invocation. *Repro: add a dead-code fn, trigger a write — hook is green; CI is red.*
- **C77** — **Post-edit hook runs `flutter analyze` without `--fatal-infos` — passes what CI rejects** — `.claude/hooks/post-edit-validation.sh:64-66`. Same drift: info-level lints (e.g. `avoid_print`) exit 0 in the hook, non-zero in CI. *Repro: add a `print()` to any .dart file.*
- **C78** — **`Cargo.lock` is gitignored for a binary crate** — `.gitignore:4`. `git ls-files engine/Cargo.lock` is empty. The engine ships a cdylib to end users; without the lock, CI resolves transitive deps (cpal, rubato, symphonia, parking_lot) at build time → two runs of the same commit can differ. *Repro: `git ls-files engine/Cargo.lock` — empty.*
- **C79** — **`pubspec.lock` is gitignored for a Flutter app** — `.gitignore:13`. Same reproducibility hole on the Dart side; Flutter docs say commit it for applications. *Repro: `git ls-files ui/pubspec.lock` — empty.*

### Medium

- **C3** — **Muted/non-solo tracks run their VST3 FX chain on live signal in the playing path** — `engine/src/audio_graph/renderer.rs:1045`. `process_effect_chain_block` is always called with `silent=false`; `audible` is only checked at Pass 3 (1078) to skip summing. A muted track's plugin burns CPU on real input every buffer. The stopped path does this right (638-648). Fix: pass `!audible`. *Repro: VST3 instrument on a muted track — same CPU stopped vs playing.*
- **C6** — **Delay/Chorus buffer capacity is fixed at construction from 48 kHz; no resize** — `engine/src/effects.rs:680`. `Delay::new()` allocs 96000 samples, `Chorus::new()` 2400 (`:1064`); neither resizes on rate change. At 96 kHz the delay holds 1 s not 2 s (a 1500 ms delay wraps into garbage). *Repro: 96 kHz device, Delay 1500 ms.*
- **C11** — **One-pole synth filter cutoff has no frequency-domain mapping** — `engine/src/synth.rs:322`. `coeff = cutoff` directly (cutoff=1.0 is correctly pass-through), but cutoff=0.5 maps to no defined Hz and is rate-independent while the filtered frequency isn't → timbre changes between 44.1/96 kHz with no param change. *Repro: cutoff 0.5, switch device rate.*
- **C12** — **FTZ/DAZ MXCSR flags set but never restored — leaks out of the callback on x86_64** — `engine/src/audio_graph/renderer.rs:534`. Sets FTZ/DAZ per buffer, never restores. On x86_64 + CPAL (reused OS threads) any later non-audio work on that thread permanently runs with altered FP semantics. Fix: save/restore MXCSR around the callback. *Repro: x86_64 Linux, check MXCSR outside the audio path post-start.*
- **C18** — **`start_time`/`end_time` loop-region export fields are silently ignored** — `engine/src/export/options.rs:133`. Set via `with_range()`, documented as the export region, but never read; `render_offline()` always renders frame 0 → full duration. A caller exporting a selection gets the full mix. *Repro: `start_time=5.0, end_time=10.0` — file contains full project.*
- **C19** — **MP3 ffmpeg stdin not closed before `wait_with_output` — pipe-buffer/zombie risk** — `engine/src/export/mp3.rs:162`. On early ffmpeg exit, `write_all` returns broken-pipe and the caller returns without reaping the child (zombie); large stderr before stdin closes can deadlock the pipe on some platforms. Fix: `drop(child.stdin.take())` first. *Repro: feed a corrupt PCM stream.*
- **C20** — **`load_project` holds the audio_graph lock across the whole restore + audio-clip loop** — `engine/src/api/project.rs:84`. Held through VST3 loads, synth setup, track creation, and the clip-attach loop. Any concurrent FFI lock (a background timer/notification querying tracks) deadlocks silently. Masked by the UI disabling controls during load. *Repro: `get_tracks_ffi()` from a Dart Timer during `load_project_ffi()`.*
- **C21 / C62** — **VST3 restored with hardcoded `block_size=512`, ignoring the saved buffer preset** — `engine/src/audio_graph/project.rs:656`. The buffer preset is restored a few lines earlier but not read back; plugins that size lookahead/internal buffers at init get wrong latency compensation until a manual device restart. *Repro: save with High Stability, reload, render offline.*
- **C22** — **Recorder `stop_recording` hardcodes 48 kHz for duration + clip sample_rate** — `engine/src/recorder.rs:192`. On a 44.1 kHz device the duration and `AudioClip.sample_rate` are wrong by the rate ratio; playback (which assumes 48 kHz) runs 8.84% too fast/sharp. *Repro: record on a 44100 Hz system, play back.*
- **C27** — **`g_last_error` is an unmutexed global `std::string`, written from audio thread + read from UI thread** — `engine/vst3_host/vst3_host.cpp:46`. `set_error()` runs in `vst3_process_audio()` (921) and `vst3_process_midi_event()` (937/943/1010/1017) on the audio thread; `vst3_get_last_error()` (1666) reads on the UI thread. Concurrent read/write of `std::string` is UB. *Repro: drive underruns into the error path while calling `get_vst3_state_ffi`.*
- **C28** — **`processContext` is always null — tempo-sync VST3 effects/instruments silent or wrong** — `engine/vst3_host/vst3_host.cpp:911`. Plugins checking `kPlaying` stay frozen; tempo-sync LFOs/arps fall back to wrong defaults. `ppqPosition` is also hardcoded 0 (`:952`). *Repro: load a tempo-synced tremolo at 1/4 — no sync to BPM.*
- **C29** — **`vst3_process_audio` always sets `numInputs=1` with a non-null bus — UB on 0-input instruments** — `engine/vst3_host/vst3_host.cpp:899`. Strict instrument plugins that declare 0 audio-input buses see a mismatched `numInputs` → UB in their `process()`. Fix: query `getBusCount(kAudio,kInput)` at init. *Repro: load an instrument with 0 kAudio/kInput buses.*
- **C35** — **AUDIO_GRAPH lock held for the entire synchronous offline render during export** — `engine/src/api/project.rs:182-193`. `export_*` lock the graph then call `render_offline(duration)` — ~8.6M frames for a 3-min/48 kHz project with the lock held. Every other FFI call blocks; the 100 ms progress timer can't interleave (the Dart loop is blocked by the sync FFI call) → progress bar never moves. *Repro: export a 2-min project, call any engine fn from a background timer.*
- **C40** — **Loop auto-follow rounds to 4-beat bars regardless of time signature** — `ui/lib/screens/daw_screen.dart:2240`. `newLoopEnd = (longestEnd/4).ceil()*4.0` hardcodes 4; in 3/4 or 7/8 the loop snaps to the wrong bar after every note edit. `timeSignatureNumerator` is already on `this`. *Repro: 3/4 project, 3-bar clip, draw a note — loop end jumps to 4 beats.*
- **C41** — **Chord-preview `Future.delayed` NoteOff fires after PianoRoll dispose; chord voices not tracked** — `ui/lib/widgets/piano_roll/audition_mixin.dart:81`. The 500 ms delayed NoteOff checks `audioEngine != null` (the engine outlives the widget) but not `mounted`; chord notes aren't in `currentlyHeldNote`, so closing within 500 ms leaks all chord voices. *Repro: click a chord, close the editor within 0.5 s.*
- **C48** — **`RecordingCompleteCommand._applyState` restores only startTime for overlap-trimmed clips** — `ui/lib/services/commands/clip_commands.dart:1244`. For a clip present in both snapshots (trimmed, not deleted) it calls `setClipStartTime` but not `setClipOffset`/`setClipDuration`; undo restores the UI but the engine keeps the trimmed region. *Repro: clip at bars 1-4, record from bar 2 (trims to 1-2), undo — UI full, engine plays 1-2.*
- **C49** — **Track reorder (drag-and-drop) is not wrapped in a Command — not undoable** — `ui/lib/screens/daw_screen.dart:1070`. `_onTrackReordered()` mutates `trackController` directly; `ReorderTrackCommand` exists but is never instantiated. *Repro: drag a track, Cmd+Z — nothing.*
- **C50** — **MIDI clip consolidation bypasses the undo graph entirely** — `ui/lib/screens/daw_screen.dart:2406`. (Same wired method as C37, listed separately for the undo-graph lens.) Consolidating N clips is destructive and irreversible with no `CompositeCommand`. *Repro: select 2+ clips, right-click Consolidate, Cmd+Z.*
- **C58** — **`_loadUILayout` swallows all exceptions with no log — corrupt layout == absent** — `ui/lib/services/project_manager_native.dart:246-258`. One malformed field discards the whole layout (panel sizes, zoom, colors, loop region, time-sig denominator) → silent reset to defaults; the caller can't tell "no file" from "corrupt file". *Repro: corrupt any field in ui_layout.json, reopen.*
- **C59** — **`arrangementSnap` is not persisted — always resets to Bar on reload** — `ui/lib/services/project_persistence.dart:150-193`. No field on `UILayoutData`; `collect()`/`applyLayout()` don't carry it. *Repro: set 1/16 snap, save, reopen — Bar.*
- **C60** — **Crash-recovery restoration uses stale tempo — notes shift off-grid** — `ui/lib/screens/daw/mixins/daw_project_mixin.dart:848-860`. ### Recommended next theme

Frame the next cycle as **"Correct on real hardware, honest about failure"** — a second trust/correctness pass, not feature work.

- **Primary — "Right on every device, right after undo"** (backlog #1–#7, plus the test net #13). Two buckets that hit users every session: (a) the **sample-rate sweep** (#3) — the single biggest *latent* footprint: every time-based effect, recording, and VST3 plugin is silently wrong on the 44.1 kHz interfaces a real musician plugs in, and it surfaces as eight separate bugs from one root cause; and (b) the **undo + corruption cluster** (#1, #2, #4–#7) — a clip that plays from the wrong beat after Cmd+Z (C46/C63, *critical*), a UI that deadlocks on the normal FX-edit workflow (C32, *critical*), a project that drops clips on reload (C66), a save that lies about succeeding (C55). Most are S/M effort; #1, #2, #5, #7 are S. A save/reload fidelity test plus an execute→undo→execute command test (part of #13) lock several of these at once. **Highest signal-to-effort, directly resumes the dogfood beat, and it clears two criticals.**

- **Alternative — "VST3 fidelity"** (backlog #17, plus the data races C27/C29). This makes hosted plugins behave correctly with real DAWs (tempo sync, instrument buses, error-string safety). It's genuinely valuable and the `g_last_error` race is real UB — but the cost is that it touches the C++ host (slower iteration, the committed-`.a` rebuild dance from `vst3-cpp-lib-rebuild`), benefits only users who load third-party plugins, and leaves the two *criticals* and the silent-corruption paths unfixed for everyone else. Higher cost, narrower audience.

**Recommendation:** lead with the device-correctness + undo/corruption cluster (it contains both criticals, most of the silent data loss, and the cheapest wins), and stand up the engine `api`/`ffi` test net (#13) in the same cycle so the round-trip fixes can't regress. Slot VST3 fidelity as the centerpiece of the *following* cycle, once those tests exist to catch C++ regressions. Do the correctness cluster **before any v0.6 feature work** — shipping the drum-kit engine on top of a UI that deadlocks on FX-edit and an engine that's 8.8% off on 44.1 kHz only buries the problems deeper.
